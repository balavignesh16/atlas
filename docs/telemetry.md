# ATLAS Telemetry Foundation

This document outlines the telemetry architecture for ATLAS LAB established in Milestone 2.1. The core observability stack utilizes OpenTelemetry (OTel) to provide distributed tracing and basic request metrics.

## 1. Why OpenTelemetry?
OpenTelemetry provides a standardized, vendor-agnostic framework for capturing observability data. By leveraging OTel, ATLAS can collect traces and metrics consistently across all services without locking into a specific backend provider.

## 2. Trace vs Span
- **Trace**: Represents the end-to-end journey of a single request across the distributed system (e.g., from the client, through the Gateway, to the Order Service, and down to the Inventory/Payment Services).
- **Span**: A single logical operation within a trace (e.g., the `PaymentClient` making an HTTP request, or the `InventoryController` processing a reservation). Spans have a parent-child relationship, forming a directed acyclic graph that represents the trace structure.

## 3. Trace ID vs Correlation ID
- **Trace ID**: Automatically generated by OpenTelemetry at the edge (Gateway) and propagated via W3C `traceparent` headers. It uniquely identifies the entire distributed operation for observability tooling.
- **Correlation ID** (`X-Correlation-ID`): An application-level identifier used for business tracing and structured logging. 
- **Distinction**: We maintain both. The `X-Correlation-ID` is preserved in the HTTP headers and added as a Span Attribute (`correlation_id`) so that business logs and OTel traces can be cross-referenced seamlessly.

## 4. Service Identity
Stable service names are defined via the `spring.application.name` property and OTel Resource Attributes. 
The instrumented services are:
- `atlas-gateway`
- `atlas-order-service`
- `atlas-inventory-service`
- `atlas-payment-service`

## 5. OTLP (OpenTelemetry Protocol)
We use OTLP over HTTP to export data from the Spring Boot Micrometer Tracing bridge to the OpenTelemetry Collector. The default endpoints are `/v1/traces` and `/v1/metrics`.

## 6. Collector Architecture
The system uses the OpenTelemetry Collector deployed alongside the services in `docker-compose.yml`.
- **Image**: `otel/opentelemetry-collector:0.106.1`
- **Role**: Receives OTLP data and processes it.
- **Exporters**: Currently configured with a `debug` exporter for development visibility. It does NOT currently forward to Jaeger, Tempo, or Elasticsearch.

## 7. Telemetry Flow
1. **Generation**: Spring Boot Micrometer (`micrometer-tracing-bridge-otel`) automatically instruments HTTP servers and `RestClient` calls.
2. **Context Propagation**: W3C `traceparent` headers are automatically injected into downstream requests.
3. **Export**: Spans and metrics are pushed to the `otel-collector` container on port `4318`.
4. **Processing**: The Collector outputs the telemetry to stdout for verification.

## 8. How to Run the Telemetry Stack
Run the standard docker-compose environment:
```bash
make docker-build
docker-compose up -d
```
The `otel-collector` service will start automatically alongside the business services.

## 9. How to Inspect/Verify Telemetry
Since M2.1 utilizes the `debug` exporter, traces and metrics are printed directly to the Collector's logs:
```bash
docker-compose logs -f otel-collector
```
You will see `TracesExporter` output displaying Trace IDs, Span IDs, parent-child linkages, and service names.

## 10. Intentional Omissions (What is NOT Implemented)
In M2.1, the focus is strictly on the foundation. The following are intentionally excluded:
- Centralized log aggregation (Elasticsearch/Loki).
- Visual dashboards (Jaeger/Tempo/Grafana).
- AI reasoning, root-cause analysis, and anomaly detection.
- Kafka or event buses.
- Manual spanning around internal methods (we rely on automatic instrumentation).
